## 1. 先纠偏：四者不在同一个维度

把它们当成"四个候选方案"来选，是个常见误区。它们回答的是不同层面的问题：

| 概念 | 本质 | 类比 |
| --- | --- | --- |
| **本体论 Ontology** | 概念模型 / Schema：定义"有哪些类、有哪些关系、约束是什么" | 数据库表结构定义 |
| **知识图谱 KG** | 数据结构：按 schema 填进去的实体-关系实例（三元组） | 按表结构填好数据的库 |
| **RAG** | 检索范式：**查询时**检索原文片段，拼进上下文再让 LLM 回答 | SELECT + 拼装 prompt |
| **LLM-wiki** | 知识形态：**写入时**用 LLM 把语料编译成结构化词条，查询时直接读词条 | 预编译的物化视图 / 缓存 |

所以正确的组合关系是：

```
本体论（定义结构）
   ↓ 约束
知识图谱（按结构填数据）  ←  二者是"结构 + 数据"，管的是知识怎么存
   
RAG（查询时检索原文）     ←  二者是"读原文 vs 读预编译"，管的是什么时候算
LLM-wiki（写入时编译词条）
```

真正要决策的是**两个独立问题**：

1. **知识怎么组织**：纯文本块 / 结构化图谱 / 两者结合？
2. **什么时候计算**：查询时检索原文（RAG），还是写入时预编译词条（Wiki）？

## 2. 四个方案的真实代价

| 维度 | RAG（原文分块） | 知识图谱 + 本体 | LLM-wiki |
| --- | --- | --- | --- |
| 构建成本 | 低：切块 + 嵌入，几小时 | **高**：本体设计 + 实体/关系抽取 + 消歧 + 校验 | **高**：逐知识点调用 LLM 编译 |
| 查询成本 | 每次都要检索 + 生成 | 图遍历便宜，但仍需生成 | **低**：直接读词条，可省检索与长上下文 |
| 可溯源性 | **强**：每块带册次/页码，可原文引用 | 中：三元组能带出处，但 LLM 抽取时易丢失 | **弱**：词条是 LLM 重写稿，已不是原文 |
| 知识腐坏风险 | 无（存的就是原文） | **有**：抽取的三元组可能错，且错得隐蔽 | **有**：编译时就可能引入幻觉，且会随语料更新过期 |
| 维护成本 | 低：语料变了重跑切块 | **高**：换教材版本要重建图谱 | **高**：换版要重编译受影响词条 |
| 覆盖完整性 | **完整**：原文全覆盖 | 不完整：只有抽出来的实体才在图上 | 不完整：只有编译过的知识点才有词条 |
| 擅长的问题 | "这一课讲了什么"、"原文怎么说" | 多跳推理、"A 和 B 什么关系" | 高频概念的稳定解释 |
| 不擅长 | 跨文档全局归纳（需 map-reduce 补） | 需要原文细节的问答 | 长尾问题、需要原文的问答 |

## 3. 本项目的语料与场景特征

选型不能脱离数据。当前已采集（杭州小学）：

| 指标 | 实测值 |
| --- | --- |
| 册数 / 体积 | 94 册 / 4.64 GB |
| 学科 | 语文、数学、英语、道德与法治、科学、艺术·音乐、艺术·美术、书法（8 个） |
| 年级 | 一年级 14 册 … 六年级 14 册，全覆盖 |
| 单册页数（估） | 80–150 页，合计约 **1 万页** |
| 纯文本量（估） | 文本层可用的学科每册 3–8 万字；合计约 **300–500 万字** |
| 需 OCR 的部分 | 17 册单册 >80MB（科学 12 册、书法 7 册等）为高清图版；美术/音乐大量插图，合计约 **4000–5000 页需 OCR** |
| 更新频率 | 低：教材数年一换，语料基本静态 |
| 运行环境 | 单机 Windows，无 GPU，预算有限 |

场景特征（决定选型的关键）：

- **使用者是小学生和家长**：讲错等于误人子弟，准确性优先级最高。
- **硬约束：可溯源**。回答必须能指出"三年级上册第 X 页"，检索不到要说"教材里没有"。
- **查询以局部为主**：绝大多数是"这一课讲什么"、"这个概念怎么解释"、"出几道题练练"，元数据能精确定位到册次。
- **语料规模小**：300–500 万字、约 3–5 万个块。全量向量化在 CPU 上也就几十分钟，成本几乎可忽略。

### 3.1 语料范围扩展：教材 + 教辅 + 课外书（★）

教材之外还要纳入**教辅**（讲法、梯度题、易错点）与**课外书**（整本书阅读、主题拓展），否则只能"答"不能"教"。
但这**不改变本文的选型结论**——RAG 仍是底座，因为可溯源性要求没有变，只是依据要**分层**：

| 层 | 角色 | 能否作为事实依据 |
| --- | --- | --- |
| 教材 core | 唯一事实源 | ✅ 是 |
| 教辅 aid | 方法层（怎么讲、怎么练） | ❌ 只能作讲法与练习依据，须标 `[教辅]` |
| 课外 ext | 素材层（读什么、什么情境） | ❌ 不参与事实判定 |

要点：

1. **分层必须在检索阶段就分开**（元数据 `source_tier` 过滤），不能混进同一个候选池让模型自己挑——
   否则教辅的精炼讲解会凭借"更易读"在语义检索里挤掉教材原文，悄无声息地破坏可溯源性。
2. **课外书必须有锚点才能入库**（挂语文要素 / 单元主题 / 教材"快乐读书吧"推荐书目）；无锚点的内容不做。
3. 语料总量会增长（预计增到 800–1500 万字），但**仍在"小语料"量级**，混合检索 + 重排的结论不变。
4. L2 词条层可以**优先编译教辅侧的高频讲解**（如"分数怎么讲"），因为这类内容稳定、重复查询多；
   但词条仍要回链教材页码，保持"一键回原文"。

## 4. 结论：RAG 打底 + 目录即图谱 + Wiki 缓存热点

### 4.1 结论

> **以 RAG 为唯一底座，用"教材目录"充当知识图谱骨架（配轻量本体），
> 仅对高频知识点用 LLM-wiki 做预编译缓存。
> 不做重型知识图谱，不做全量本体工程。**

**分层原则：每层必须对应一个明确的失败模式。没有对应问题的层就是过度设计。**

| 层 | 解决什么失败模式 | 技术 | 建不建 |
| --- | --- | --- | --- |
| **L0 原文层** | **编造**（说了教材里没有的话） | RAG，页级引用 | ✅ 永久底座 |
| **L1 结构层** | **找错范围**（定位不准、串册） | 目录树 + 元数据过滤 + 轻量本体（≤6 关系）+ **学科结构化表** | ✅ 建，成本极低 |
| **L2 词条层** | **慢 / 答案不稳定** | LLM-wiki 预编译 | ⭕ 按需，只做热点 |
| ~~L3 实体图谱~~ | 多跳推理 | 三元组 | ❌ 现在不建 |

**实证：看似需要图谱的查询，结构层就能答**

「分数」在数学各册的分布（一年级 1 页 → 三年级上 21 页 → 五年级 43 页 → 六年级 43 页）
就是"跨册知识演进视图"——**用「册次 + 页」元数据过滤加词频统计，1 秒出结果**，
不需要任何实体-关系三元组。

**★ 学科结构化表是"隐藏的 L1.5"，价值最高却最容易被忽略**：
语文字词表 / 数学题库 / 英语词汇句型表 / 科学实验清单 —— 走**精确匹配**（SQLite）、不调 LLM、
准确率 ≥99%。它们是"确定性"的真正来源，比任何图谱都实在。

三层，能力递增，可逐级交付：

| 层 | 形态 | 作用 | 是否必需 |
| --- | --- | --- | --- |
| L0 原文层 | 切块 + 向量 & BM25 混合索引 + 元数据过滤 | 保底：**所有回答都能溯源到册次页码** | **必需，先做** |
| L1 结构层 | 目录树 + 知识点清单（学科→册次→单元→课→知识点），配轻量本体（关系类型约 6 种） | 精确导航、按课检索、跨册定位"分数在哪几册出现" | 必需，成本很低 |
| L2 词条层 | LLM-wiki：高频知识点的结构化词条（定义 / 例子 / 易错点 / 常见问法 / **引用页码**） | 降延迟、降在线成本、答案更稳定 | 可选，按需增量生成 |

### 4.2 为什么 RAG 必须是底座

这是由**硬约束**决定的，不是性能权衡：

- 只有原文层能保证"引用的是教材原文"。Wiki 词条是 LLM 重写稿，图谱三元组是抽取结果，两者都在原始信息上有损且可能引入幻觉。
- 一旦 LLM 改写过，就无法对孩子说"书上第 32 页就是这么写的"。
- 覆盖率：原文层是 100%，图谱和 wiki 都是子集。子集方案在长尾问题上会直接答不出来或被迫编。

因此 L0 不是"过渡方案"，而是**永久底座**；L1/L2 只是加在它上面的加速与导航层。

### 4.3 知识图谱：待验证，不预设排除（★）

**本节不是结论，是待验证的假设。** 当前证据倾向"先不建"，但**设计阶段不做硬性排除**。
下面同时列出两面的理由，并给出**用什么实验来判定**——而不是靠论证下结论。

**反对建（风险与成本）**

1. **抽取质量是最大风险**。自动抽的三元组会有错误关系，且错得隐蔽——比"检索不到"更危险。给小学生用，宁可答"教材里没有"，也不能给一条错误的关系链。
2. **教材自带高质量骨架**。"单元 → 课 → 知识点"由出版社精心编排，目录页规则抽取即可，准确且几乎零成本。
3. **多数"定位型"需求用元数据过滤即可**。"三年级上册数学第三单元讲了什么"本质是过滤，不是图遍历。
4. **语料规模不大**（约 500 万字），图在千万级语料上的多跳优势未必用得上。
5. **换版成本**。改版要重建抽取与校验，原文层只需重跑解析。

**支持建（此前被低估的一面）**

1. **真正的多跳需求确实存在**：螺旋上升（同一要素在各年级的深度递进）、先修关系（不会 X 是因为没掌握 Y）、跨册演进——**这些不是检索问题，是推理问题**，元数据过滤替代不了。
2. **归因与计划依赖关系**：错因归到"先修未掌握"、提升计划的排序依赖先修关系，都超出"过滤"的能力。
3. **挂载扩展书籍**时，"这段与那篇课文适配"本质上就是一条关系。
4. 本体方案 docx 设计 37 类关系，说明语文侧的关系需求确实丰富（多数可用属性实现，但不是全部）。

> **★ 承认评估框架的偏差**：此前一直用"**检索准确率**"衡量图谱，得出"元数据过滤能替代"的结论。
> 但图谱的价值主要在**推理与约束**，不在检索——**只测检索，必然得出"图谱无用"的错误结论**。

**判定方式：做一个单元级试点，别靠论证下结论**

| 项 | 设计 |
| --- | --- |
| 试点范围 | 一个单元（如三上语文第三单元，约 4 课） |
| 做法 | 按 docx 的 L0–L3 抽取节点与关系，**人工校对**以保证正确（先排除抽取噪声干扰） |
| 对照 | A：RAG + 属性过滤（无图）　vs　B：图遍历 + RAG（有图） |
| 测试集 | 20 个真实问题，**其中多跳/推理类 ≥8 条**（"这个要素在几年级出现过""学这个之前要会什么"） |
| 指标 | 答案准确率、拒答率、**归因质量**、**计划合理性**（后两项人工评） |
| 成本 | 抽取耗时、人工校对耗时、换版重做成本 |
| **决策门** | B 在**多跳/推理类**问题上显著优于 A，且抽取准确率 ≥90% → 建；否则先不建，但**保留字段与接口** |

**在此之前**：不建图谱，但**不关闭这个选项**——数据模型为节点/关系预留位置，切换成本可控。

### 4.4 本体论：关系要少，属性要多（★ 关键澄清）

**"轻量"指的是关系类型少，不是属性少**——这两件事必须分开看：

| | 数量 | 理由 |
| --- | --- | --- |
| **关系类型** | 现阶段 ≤6 种（**待 §4.3 试点验证**） | 关系靠抽取，错了隐蔽；但螺旋 / 先修等可能是真需求，不预设排除 |
| **属性维度** | **越丰富越好** | 属性是挂载的抓手，决定能不能找到扩展资料 |

**为什么属性必须丰富**：属性决定**挂载精度**。上传的课外书能挂到多细，取决于教材侧有多少可对齐的属性——

| 挂载精度 | 需要的属性 | 效果 |
| --- | --- | --- |
| 书级 | 无（整本书检索） | 找到"汪曾祺的书"，还要在里面大海捞针 |
| **作者级** | 作者 | 系统知道"这一课是汪曾祺写的"，直接定位他的作品集 |
| **片段级** | 作者 + 体裁 + 主题 + **写作手法** | 直接给出"他写看车匠、看灯笼铺那段"——**可核对的原文片段，而不是空谈** |

用户上传扩展书籍的全部价值，就押在这张属性表上。**属性贫乏 = 挂载粗 = Agent 只能空谈。**

**实证：属性能否规则抽取（语文册）**

| 属性 | 实测 | 获取方式 |
| --- | --- | --- |
| **作者** | **226 处，可抽出 170 位作者**（老舍、沈从文、朱自清、冯至、叶永烈、肖复兴…） | ✅ **规则**（课文注释"① 本文作者××"），可靠 |
| 体裁·古诗 | 49 处 | ✅ 规则（目录 + 标题特征） |
| 体裁·童话 / 神话 / 寓言 | 17 / 12 / 10 处 | ⚠️ 部分规则 |
| 体裁·散文 / 说明文 | 4 / 1 处 | ❌ 规则覆盖不了 → **需 LLM** |
| 主题、写作手法、情感基调 | 教材无标记 | ❌ **需 LLM 标注** |

→ **作者属性天然可靠且量大（170 位），这是挂载作家作品集的现成锚点**；其余属性靠 LLM 补齐。

**★ 属性分两级，用法不同**

| 级别 | 来源 | 用途 | 容错 |
| --- | --- | --- | --- |
| **可靠属性** | 规则抽取（册次/单元/课/作者/题型/页码） | **硬过滤**（WHERE 条件） | 错不起，必须准 |
| **推断属性** | LLM 标注（主题/手法/情感/难度） | **软排序**（加权打分） | 错了只是排偏，不致命 |

**★ 为什么可以放心让属性变多：错误后果分级**

| 层 | 错了的后果 | 因此 |
| --- | --- | --- |
| L0 原文 | **教错孩子** | 必须 100% 原文、可溯源 |
| **L1 属性** | **只是找不到 / 找偏** | ← **可以大胆用 LLM 标注** |
| L2 词条 | 可能是错的重写稿 | 必须带引用、可一键重建 |

属性标注错了，最坏结果是"这段没匹配上"或"匹配到一段不太相关的"——**但匹配到的仍然是原文，可核对**。
它不会让孩子学到错误内容。这与"让 LLM 直接生成内容"是本质区别。

**★ 属性从检索需求倒推，不从本体完备性正推**

要问的不是"一篇课文有哪些属性可以标"，而是"**我要找什么**"：
教作文时要找"写人细节描写的片段" → 才需要 `写作手法=细节描写` + `对象=人物` 这两个属性。
正推会得到一张学术上很美、工程上无人使用的本体。**没有对应检索需求的属性，一律不加。**

#### 4.4.1 挂载对齐表：教材侧 ↔ 扩展书籍侧

**挂载的本质是两边属性对齐**。教材侧与上传书籍侧必须标**同一套属性**才能匹配上：

| 属性 | 教材侧来源 | 书籍侧来源 | 用途举例 |
| --- | --- | --- | --- |
| **作者** | 课文注释（**规则**，170 位） | 书名 / 目录（规则） | 讲《昆虫备忘录》→ 定位汪曾祺作品集 |
| 体裁 | 目录 + LLM | LLM 标注 | 学"说明文"→ 找同类说明文片段 |
| 主题（写人/记事/写景/状物） | LLM | LLM | 习作"写一个人"→ 找写人片段 |
| **写作手法**（细节/对比/比喻/感官） | LLM | LLM | 孩子问"怎么写生动"→ 给出用了细节描写的**原段** |
| 语文要素 / 策略单元 | 单元页（规则） | — | 本单元练"提问"→ 找适合提问的段落 |
| 情感基调 | LLM | LLM | 朗读与理解指导 |
| 难度 / 适龄 | 年级（规则） | LLM | 不选超出当前年级太多的片段 |

上传一本书时：切分 → 每段标上这套属性 → 存 `ext` 层（记 `tier=ext`）。
查询时先取当前课的属性，再到 ext 层做**属性过滤 + 语义检索**。
**这就是"属性丰富 → Agent 更容易找到资料"的完整机制。**

其它学科同理，属性即挂载锚点：

| 学科 | 核心属性 | 扩展资料按什么挂 |
| --- | --- | --- |
| 数学 | `kp_id` + `type` + **`thinking_tags`** | 按**思维方法**挂（转化 / 画图 / 建模），**不是按难度挂** |
| 英语 | 词汇表 + 句型表 | 按"当前册已学范围"挂（范围锁定） |
| 科学 | 实验 / 材料 / 安全 | 按实验主题挂（虚拟仿真 + 探究素材） |

```
学科 ──has──▶ 册次 ──has──▶ 单元 ──has──▶ 课 ──has──▶ 知识点
                                                        │
知识点 ──prerequisite_of──▶ 知识点      （先修，如"分数加减"先修"同分母分数"）
知识点 ──related_to──▶ 知识点          （相关）
知识点 ──appears_in──▶ 册次/页码       （出现位置，跨册螺旋上升）
```

关系类型控制在 **6 种以内**。先修关系不必全量抽取——用"知识点在教材中首次出现的册次顺序"自动推导一个初始版本，再人工校对（规模约 1000–3000 条知识点，可控）。

**判断标准**：如果某条关系无法用规则从目录/页码推导、必须靠 LLM 猜，那它大概率不值得现在做。

### 4.5 为什么 LLM-wiki 只做"热点缓存"

Wiki 的经济学是：**高频读取摊薄一次编译成本**。

- 语料只有 500 万字，L0 检索本身就很便宜 → 全量 wiki 化省不了多少钱，却要付出编译成本和腐坏风险。
- 但**热点确实存在**："什么是分数"、"乘法口诀"、"的地得用法"这类问题会被反复问，且每次都要重排 + 生成 → 值得预编译。
- 做法：**按需增量**。记录查询日志，对 Top-N 高频知识点（或按教材目录预先圈定的核心概念，约 500–2000 个）生成词条，**每条必须带引用页码**，命中 wiki 时仍要能一键跳回原文核对。
- 关键约束：**wiki 只是缓存，不是事实源**。原文层不一致时以原文为准，提供 `--rebuild` 重编译。
