# 知识库方案选型

> 回答一个问题：**教材知识库到底该建 LLM-wiki、本体论、知识图谱，还是 RAG？**
> 本文先纠偏（这四者不在同一维度），再结合本项目语料特征给出选型、理由、落地路线与回退条件。
> 工程实现细节见 `docs/系统设计文档.md`。

---

## 1. 先纠偏：四者不在同一个维度

把它们当成"四个候选方案"来选，是个常见误区。它们回答的是不同层面的问题：

| 概念 | 本质 | 类比 |
| --- | --- | --- |
| **本体论 Ontology** | 概念模型 / Schema：定义"有哪些类、有哪些关系、约束是什么" | 数据库表结构定义 |
| **知识图谱 KG** | 数据结构：按 schema 填进去的实体-关系实例（三元组） | 按表结构填好数据的库 |
| **RAG** | 检索范式：**查询时**检索原文片段，拼进上下文再让 LLM 回答 | SELECT + 拼装 prompt |
| **LLM-wiki** | 知识形态：**写入时**用 LLM 把语料编译成结构化词条，查询时直接读词条 | 预编译的物化视图 / 缓存 |

所以正确的组合关系是：

```
本体论（定义结构）
   ↓ 约束
知识图谱（按结构填数据）  ←  二者是"结构 + 数据"，管的是知识怎么存
   
RAG（查询时检索原文）     ←  二者是"读原文 vs 读预编译"，管的是什么时候算
LLM-wiki（写入时编译词条）
```

真正要决策的是**两个独立问题**：

1. **知识怎么组织**：纯文本块 / 结构化图谱 / 两者结合？
2. **什么时候计算**：查询时检索原文（RAG），还是写入时预编译词条（Wiki）？

## 2. 四个方案的真实代价

| 维度 | RAG（原文分块） | 知识图谱 + 本体 | LLM-wiki |
| --- | --- | --- | --- |
| 构建成本 | 低：切块 + 嵌入，几小时 | **高**：本体设计 + 实体/关系抽取 + 消歧 + 校验 | **高**：逐知识点调用 LLM 编译 |
| 查询成本 | 每次都要检索 + 生成 | 图遍历便宜，但仍需生成 | **低**：直接读词条，可省检索与长上下文 |
| 可溯源性 | **强**：每块带册次/页码，可原文引用 | 中：三元组能带出处，但 LLM 抽取时易丢失 | **弱**：词条是 LLM 重写稿，已不是原文 |
| 知识腐坏风险 | 无（存的就是原文） | **有**：抽取的三元组可能错，且错得隐蔽 | **有**：编译时就可能引入幻觉，且会随语料更新过期 |
| 维护成本 | 低：语料变了重跑切块 | **高**：换教材版本要重建图谱 | **高**：换版要重编译受影响词条 |
| 覆盖完整性 | **完整**：原文全覆盖 | 不完整：只有抽出来的实体才在图上 | 不完整：只有编译过的知识点才有词条 |
| 擅长的问题 | "这一课讲了什么"、"原文怎么说" | 多跳推理、"A 和 B 什么关系" | 高频概念的稳定解释 |
| 不擅长 | 跨文档全局归纳（需 map-reduce 补） | 需要原文细节的问答 | 长尾问题、需要原文的问答 |

## 3. 本项目的语料与场景特征

选型不能脱离数据。当前已采集（杭州小学）：

| 指标 | 实测值 |
| --- | --- |
| 册数 / 体积 | 94 册 / 4.64 GB |
| 学科 | 语文、数学、英语、道德与法治、科学、艺术·音乐、艺术·美术、书法（8 个） |
| 年级 | 一年级 14 册 … 六年级 14 册，全覆盖 |
| 单册页数（估） | 80–150 页，合计约 **1 万页** |
| 纯文本量（估） | 文本层可用的学科每册 3–8 万字；合计约 **300–500 万字** |
| 需 OCR 的部分 | 17 册单册 >80MB（科学 12 册、书法 7 册等）为高清图版；美术/音乐大量插图，合计约 **4000–5000 页需 OCR** |
| 更新频率 | 低：教材数年一换，语料基本静态 |
| 运行环境 | 单机 Windows，无 GPU，预算有限 |

场景特征（决定选型的关键）：

- **使用者是小学生和家长**：讲错等于误人子弟，准确性优先级最高。
- **硬约束：可溯源**。回答必须能指出"三年级上册第 X 页"，检索不到要说"教材里没有"。
- **查询以局部为主**：绝大多数是"这一课讲什么"、"这个概念怎么解释"、"出几道题练练"，元数据能精确定位到册次。
- **语料规模小**：300–500 万字、约 3–5 万个块。全量向量化在 CPU 上也就几十分钟，成本几乎可忽略。

## 4. 结论：RAG 打底 + 目录即图谱 + Wiki 缓存热点

### 4.1 结论

> **以 RAG 为唯一底座，用"教材目录"充当知识图谱骨架（配轻量本体），
> 仅对高频知识点用 LLM-wiki 做预编译缓存。
> 不做重型知识图谱，不做全量本体工程。**

三层，能力递增，可逐级交付：

| 层 | 形态 | 作用 | 是否必需 |
| --- | --- | --- | --- |
| L0 原文层 | 切块 + 向量 & BM25 混合索引 + 元数据过滤 | 保底：**所有回答都能溯源到册次页码** | **必需，先做** |
| L1 结构层 | 目录树 + 知识点清单（学科→册次→单元→课→知识点），配轻量本体（关系类型约 6 种） | 精确导航、按课检索、跨册定位"分数在哪几册出现" | 必需，成本很低 |
| L2 词条层 | LLM-wiki：高频知识点的结构化词条（定义 / 例子 / 易错点 / 常见问法 / **引用页码**） | 降延迟、降在线成本、答案更稳定 | 可选，按需增量生成 |

### 4.2 为什么 RAG 必须是底座

这是由**硬约束**决定的，不是性能权衡：

- 只有原文层能保证"引用的是教材原文"。Wiki 词条是 LLM 重写稿，图谱三元组是抽取结果，两者都在原始信息上有损且可能引入幻觉。
- 一旦 LLM 改写过，就无法对孩子说"书上第 32 页就是这么写的"。
- 覆盖率：原文层是 100%，图谱和 wiki 都是子集。子集方案在长尾问题上会直接答不出来或被迫编。

因此 L0 不是"过渡方案"，而是**永久底座**；L1/L2 只是加在它上面的加速与导航层。

### 4.3 为什么不做重型知识图谱

1. **抽取质量是最大风险**。自动抽取的三元组会有错误关系，且错得隐蔽——比"检索不到"更危险。给小学生用，宁可答"教材里没有"，也不能给一条错误的关系链。
2. **教材自带高质量骨架**。"单元 → 课 → 知识点"是出版社精心编排的，直接存在于目录页，用规则就能抽取，**准确且几乎零成本**。自己抽实体关系，是在浪费这份免费的高质量结构，去换一份低质量的自动抽取结果。
3. **多数需求用元数据过滤就能解决**。"三年级上册数学第三单元讲了什么"这种问题，本质是**过滤**，不是图遍历。加个 `grade=三年级 & volume=上册 & subject=数学 & unit=第三单元` 的过滤，命中率和图遍历一样，成本低两个数量级。
4. **语料太小，图的多跳优势用不上**。图检索真正划算的是千万级语料上的多跳关联；本项目 500 万字，混合检索 + 重排已足够。
5. **换版成本高**。教材改版时图谱要重建抽取与校验，原文层只需重跑解析。

### 4.4 为什么本体论只做"轻量"的

本体论的价值在于**约束**，不在于规模。本项目只需要一张很小的 schema：

```
学科 ──has──▶ 册次 ──has──▶ 单元 ──has──▶ 课 ──has──▶ 知识点
                                                        │
知识点 ──prerequisite_of──▶ 知识点      （先修，如"分数加减"先修"同分母分数"）
知识点 ──related_to──▶ 知识点          （相关）
知识点 ──appears_in──▶ 册次/页码       （出现位置，跨册螺旋上升）
```

关系类型控制在 **6 种以内**。先修关系不必全量抽取——用"知识点在教材中首次出现的册次顺序"自动推导一个初始版本，再人工校对（规模约 1000–3000 条知识点，可控）。

**判断标准**：如果某条关系无法用规则从目录/页码推导、必须靠 LLM 猜，那它大概率不值得现在做。

### 4.5 为什么 LLM-wiki 只做"热点缓存"

Wiki 的经济学是：**高频读取摊薄一次编译成本**。

- 语料只有 500 万字，L0 检索本身就很便宜 → 全量 wiki 化省不了多少钱，却要付出编译成本和腐坏风险。
- 但**热点确实存在**："什么是分数"、"乘法口诀"、"的地得用法"这类问题会被反复问，且每次都要重排 + 生成 → 值得预编译。
- 做法：**按需增量**。记录查询日志，对 Top-N 高频知识点（或按教材目录预先圈定的核心概念，约 500–2000 个）生成词条，**每条必须带引用页码**，命中 wiki 时仍要能一键跳回原文核对。
- 关键约束：**wiki 只是缓存，不是事实源**。原文层不一致时以原文为准，提供 `--rebuild` 重编译。

## 5. 落地路线

按"先跑通、再加料"的顺序，每层都可独立交付：

| 阶段 | 内容 | 产出 | 验收标准 |
| --- | --- | --- | --- |
| **V0 跑通** | PDF 文本层抽取 + 扫描版 OCR → 按课/页切块 → BM25 + 向量混合检索 → 元数据过滤 → 带引用回答 | 能问答，答案带册次页码 | 200 题评测集上：有答案的问题命中率 ≥ 85%，无依据时正确拒答 ≥ 95% |
| **V1 结构** | 目录树抽取 → 单元/课/知识点清单 → 轻量本体与先修关系 | 能按"三年级上册第三单元"精确定位；能查"分数在哪些册出现" | 导航类问题准确率 ≥ 90% |
| **V2 词条** | 高频知识点 LLM 编译成词条（带引用） | 热点问题延迟与成本下降 | 词条与原文一致性抽检准确率 ≥ 95% |
| **V3 增强** | 图文关联（插图/表格）、公式处理、跨册知识演进视图 | 能回答"看图说一说"这类题目 | 按需 |

**V0 必须完整做完并评测达标，再动 V1。** 理由：V0 是唯一保证溯源性的层，它决定了整个系统的可信度上限。

## 6. 技术选型建议

| 环节 | 建议 | 理由 |
| --- | --- | --- |
| 文本抽取 | `pypdf` / `pdfplumber` | 文本层 PDF（语文/数学/英语/道法）直接抽，快且准 |
| OCR | `RapidOCR` / `PaddleOCR`（中文） | 科学、书法等高清图版需 OCR，CPU 可跑 |
| 切分 | 按"课"为主，页为辅；块 300–500 字，overlap 50–80 字 | 教材的课是天然语义单位，比滑动窗口更贴合 |
| 嵌入 | `bge-small-zh` / `bge-m3`（384–1024 维） | 中文效果好，CPU 可跑，3–5 万块几十分钟 |
| 关键词检索 | `bm25s` / `rank_bm25` | 教材专有名词多（"分数的初步认识"），字面匹配非常重要 |
| 融合 | RRF（倒数排名融合） | 无需调权，简单稳健；向量管语义，BM25 管精确术语 |
| 重排 | `bge-reranker-v2-m3`（仅对 top-20） | CPU 上较慢，只对小候选集用 |
| 存储 | SQLite（元数据 + BM25）+ `sqlite-vec` / `faiss`（向量） | 单机、零运维、够用；数据规模 < 1GB |
| 元数据过滤 | 学段 / 地区 / 学科 / 版本 / 年级 / 册次 / 单元 / 课 / 页码 | **过滤先于检索**：先框定"孩子当前学哪一册"，再检索 |
| 生成 | 任意中文 LLM（API 或本地） | 提示词强制引用格式，禁止无依据回答 |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| OCR 错误（尤其公式、汉字） | 科学/书法册答案不可靠 | OCR 低置信度标记；教材术语词典后校验；公式单独处理（保留图片 + 人工规则） |
| 扫描版无文本层 | 部分册检索不到 | 解析阶段输出 `text_source=ocr/text_layer` 标记，评测时单列统计 |
| 插图与图表 | 教材大量"看图回答"题型 | V0 只入图注与图周围文本；多模态留到 V3 |
| 知识点跨册重复（螺旋上升） | 回答可能引用错年级 | 检索默认限定当前年级册次，跨册结果需显式标注"四年级下册也讲过" |
| Wiki 与原文不一致 | 误导 | Wiki 仅作缓存，强制带引用页码，支持一键回原文；原文更新即失效 |
| 换教材版本 | 全部失效 | 采集层已按 `版本` 隔离目录；解析/入库产物按版本分库，换版只重跑对应版本 |

## 8. 决策记录（ADR 摘要）

**决策**：RAG 原文层为永久底座 + 目录树作图谱骨架 + 轻量本体（≤6 种关系）+ 按需 LLM-wiki 缓存。

**理由**：可溯源是硬约束，只有原文层能满足；教材自带高质量层级结构，自动抽取图谱性价比为负；语料规模小（约 500 万字），预编译收益有限而风险实在。

**放弃的方案**：
- 全量知识图谱 + 完整本体工程 —— 抽取质量风险高、换版成本大，本场景多数需求可用元数据过滤满足。
- 纯 LLM-wiki —— 破坏可溯源性，覆盖率不可控，编译期幻觉无法在查询时发现。

**何时重新评估**：
- 语料扩到全学段（小学+初中+高中，约 3000 册、上亿字）时，重估图谱的必要性；
- 多跳类问题（"学会 X 之前必须先掌握哪些"）占比超过 15% 时，加强先修关系；
- 在线成本成为瓶颈且热点足够集中时，扩大 wiki 覆盖范围。
