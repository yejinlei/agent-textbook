# 系统设计文档

> `agent-textbook`：面向小学生的教材 Agent 工程。
> 本文是工程实现蓝图：**模块划分、多 Agent 架构、学科差异化设计、数据模型、接口约定、存储布局、实施计划**。
> 知识库形态的选型论证见 `docs/知识库方案.md`；采集阶段的原理与用法见 `docs/教材提取原理与使用.md`。

---

## 1. 目标与非目标

### 目标

- 基于**本地教材原文**回答小学生与家长的问题，答案必须可溯源到册次、页码。
- 能按「孩子当前在读哪一册哪一课」精确定位，不串年级、不串版本。
- 支持讲解、举例、出题与批改、作文指导、学情跟踪。
- **按学科特性差异化处理**：语文的字词 / 阅读理解 / 习作，与数学的思维训练，走不同的检索与校验路径。
- 单机 Windows 可跑完，无需 GPU，零运维。

### 非目标

- 不做通用百科问答（语料只限教材）。
- 不做多模态大模型（V0 只处理文本与图注，插图理解留到后续）。
- 不追求自动构建大规模知识图谱（见选型文档 4.3）。
- 不做多用户、不做服务端部署。
- **不做沉浸式的"AI 同学讨论/辩论"课堂**（理由见 3.3）。

### 硬约束

| 约束 | 说明 |
| --- | --- |
| 可溯源 | 事实类回答必须带 `册次 + 页码` 引用；检索不到依据时必须回答「教材里没有」 |
| 版本隔离 | 语文统编版 / 数学人教版等不同版本产物互不混用 |
| 离线可跑 | 解析、切块、嵌入、检索全部本地完成；LLM 生成可选 API 或本地模型 |
| 不编造 | 面向小学生，宁可答「教材里没有」，也不能给出无依据内容 |
| **不代写** | 作文、作业不直接给成品，只给支架与示范（见 9.3、9.6） |

> 「可溯源」与「不编造」是**事实类任务**的约束；推导类与创作类任务用不同的校验策略，见 §9.2。这是本设计中最重要的一条分寸。

## 2. 总体架构

```
┌────────────┐   ┌────────────┐   ┌────────────┐   ┌──────────────────────────────┐
│ ① collect  │──▶│ ② parse    │──▶│ ③ index    │──▶│ ④ agents（多智能体 + 学科适配）│
│  采集 PDF   │   │  文本/OCR  │   │  切块+索引  │   │  Router→Planner→Retriever     │
│  ✅已实现    │   │  目录/字词表│   │  + 学科表   │   │  →Teacher→Guard(分模式)→输出   │
└────────────┘   └────────────┘   └────────────┘   └──────────────────────────────┘
  books/*.pdf      parsed/*.jsonl    index/*         回答+引用/解题步骤/习作指导/批改
       │                │               │                      │
       └────────────────┴───────────────┴──────────────────────┘
        data/downloads.jsonl 是贯穿全程的元数据契约（以 book_id 为键）
                                        │
                              data/memory/  学情档案（错题、掌握度）
```

| 阶段 | 输入 | 产物 | 状态 |
| --- | --- | --- | --- |
| collect | 平台接口 | `books/.../*.pdf`、`data/downloads.jsonl` | ✅ 已实现 |
| parse | `books/*.pdf` + 清单元数据 | `data/parsed/<book_id>.jsonl`（页/课/文本来源）+ **学科结构化表** | 待实现 |
| index | `data/parsed/*.jsonl` | `data/index/meta.sqlite3` + 向量库 + BM25 + **字词表/课文表** | 待实现 |
| agents | 索引 + 用户问题 + 学情 + **学科 Profile** | 回答、解题、题目、批改、习作指导、学情更新 | 待实现 |

## 3. 调研：OpenMAIC 与 DeepTutor

在设计多 Agent 之前，先研究两个同类开源项目，明确借鉴什么、不借鉴什么。

### 3.1 OpenMAIC（清华 THU-MAIC，多智能体互动课堂）

| 维度 | 做法 |
| --- | --- |
| 定位 | 从 MOOC 演进而来的 MAIC 范式：把任意主题/文档变成沉浸式互动课堂（JCST 2026 论文，清华 700+ 学生两年验证） |
| 角色 | AI 教师（不同教学风格）+ AI 助教 + 多种人格的 AI 同学 |
| 编排 | **LangGraph 多智能体状态机**，驱动轮次、讨论、协作 |
| 生成管线 | **两阶段**：① 输入主题/文档 → 结构化课程大纲；② 大纲每项 → 多媒体场景（带 TTS 的幻灯片、带评分标准的测验、互动 HTML 模拟、PBL） |
| 交互模式 | 课堂讨论 / 圆桌辩论 / 自由问答，均由状态机驱动 |
| 表现层 | 28+ 动作类型（语音、白板绘图、聚光灯、激光笔），可导出 PPTX / 互动 HTML |
| 文档解析 | MinerU |
| 栈 | Next.js + React + TS + Tailwind；OpenAI / Anthropic / Gemini / DeepSeek |

### 3.2 DeepTutor（港大 HKUDS，终身个性化辅导，40.8k stars，Apache-2.0）

| 维度 | 做法 |
| --- | --- |
| 架构 | **Agent-native**：一个 runtime 支撑 Chat / Quiz / Solve / Research / Visualize / Mastery Path / Immersive Reading 等能力，每个能力是"purpose-built loop + 共享运行时" |
| Agent 循环 | think → 调工具 → 观察结果 → 以**不带工具调用的消息**结束；`ask_user` 可暂停回合追问澄清后再恢复 |
| 上下文模型 | **sticky session context**（能力、工作区、工具、知识库、人设、模型、学习状态，跨回合持久）+ **one-time references**（文件、历史、章节、笔记、题库条目，单次注入） |
| 知识检索 | **多引擎可选**：默认 LlamaIndex（向量+BM25 混合 + 可选 cross-encoder 重排 + FAISS），另有 PageIndex（推理式检索、**页级引用**）、GraphRAG / LightRAG（图检索）、WeKnora、Kiwix、Obsidian |
| 文档解析 | 引擎可插拔：Text-only / MinerU / Docling / Tika / markitdown / PyMuPDF4LLM / LiteParse + 可选图像描述模型 |
| 索引运维 | **版本化**：重建写入新的 `version-N` 目录并保留旧版，绝不中途破坏可用索引；单文档可单独移除 |
| 检索评测 | `kb eval`：QA 集（query + gold passages）→ Recall@k / Precision@k / **nDCG@k / MRR / MAP / Hit@k**；指标是排序的纯函数、**不用模型当裁判**，可存 baseline 作回归门 |
| 记忆 | 三层文件化：L1 append-only 事件轨迹（JSONL）→ L2 按表面策展事实（Markdown，引用 L1）→ L3 跨表面综合；**刻意不用隐藏向量库**，可审计可编辑 |
| 掌握度 | Mastery Path：按类型设掌握度闸门，题库练习可达标放行 |
| 安全 | 技能导入安全门；API key 不经过模型；代码执行沙箱 |

### 3.3 本项目借鉴什么、不借鉴什么

**借鉴**

| 来源 | 借鉴点 | 落到本项目 |
| --- | --- | --- |
| DeepTutor | 单 runtime + 多 capability | 一个 Agent runtime，答疑/解题/出题/批改/习作各自一条 pipeline |
| DeepTutor | `ask_user` 澄清回路 | 作用域缺失时问「三年级上册还是下册？」，答后继续，不猜 |
| DeepTutor | sticky vs one-time 上下文 | 年级/学科/版本持久；某课某页单次注入 |
| DeepTutor | **页级引用 + 推理式检索** | 与本项目"按课/页定位、引用到页码"同构 |
| DeepTutor | 索引版本化 + 单文档增删 | 换教材版本只重跑该册 |
| DeepTutor | `kb eval` 无模型裁判 + baseline 回归门 | 直接采用（见 §11），并按学科分子集 |
| DeepTutor | 文件化、可审计的记忆 | 简化为 L1 事件 + L2 学情画像 |
| DeepTutor | 解析引擎可插拔 | Text-only / PyMuPDF4LLM / OCR 可切换（对应 17 册扫描版） |
| OpenMAIC | **两阶段生成**（大纲 → 场景） | 作文与出题都走"先定结构/要求，再逐段生成" |
| OpenMAIC | 带评分标准的测验 | 习作与解题都要先有 rubric（评分标准），再生成内容 |
| OpenMAIC | 多媒体（TTS/幻灯片） | V1 借鉴 TTS 做语文听写与朗读 |

**不借鉴**

- **不做 AI 同学圆桌辩论**。本项目的对象是小学生，多个 AI 各执一词会直接混淆认知。我们需要**一致、权威、可核对**的答案。
- **不做 TTS 讲课 / 白板特效 / PPTX 导出**（V0）。本项目是"随时提问"的答疑形态，输出以文本 + 引用为主；TTS 仅用于语文听写/朗读（V1）。
- **不照搬 DeepTutor 的规模**。它是全栈 Web 应用（FastAPI + Next.js + Docker + 多用户）；本项目保持单机 CLI 优先，零运维。

**一个重要印证**：DeepTutor 把 GraphRAG / LightRAG 仅列为**可选检索引擎之一**，默认用混合检索；这实证了 `docs/知识库方案.md` 的结论——**图是可选增强层，不是底座**。

## 5. 数据模型

以 `book_id`（平台 contentId）为主键贯穿全程。

### 5.1 Book / Page / Section / Chunk

| 实体 | 关键字段 |
| --- | --- |
| Book | `id`, `region`, `stage`, `subject`, `version`, `grade`, `volume`(册次), `title`, `path` |
| Page | `book_id`, `page_no`(物理页), `printed_no`(书上页码), `text`, `text_source`(`text_layer`/`ocr`/`empty`), `confidence`, `images`(图注) |
| Section | `book_id`, `section_id`, `unit`, `lesson`, `title`, `start_page`, `end_page` |
| Chunk | `chunk_id`(`book_id:page_no:seq`), `text`, `book_id`, `page_no`, `section_id`, `meta`(学段/学科/版本/年级/册次/单元/课，冗余供过滤), `vector` |

> 扫描版物理页码与书上页码常不一致，需维护 `page_no ↔ printed_no` 映射，否则引用页码会错。V0 先按物理页码引用并注明。

### 5.2 学科结构化实体（★ 学科差异化的数据基础）

```python
# 语文：字词基础走「查表」，不走语义检索
WordEntry:    id, book_id, char, grade, volume, lesson,
              pinyin, tone, radical, stroke_count, stroke_order,
              words[], antonyms[], synonyms[], polyphone[],
              source: 识字表|写字表|词语表, page_no

# 语文：课文整篇存取，阅读理解必须拿到完整文本
LessonText:   book_id, lesson, title, author, genre(古诗|散文|童话|说明文),
              paragraphs[], full_text, exercises[], page_range,
              strategy_unit: 提问|提高阅读速度|有目的地阅读|预测|批注

# 语文：习作要求即评分量规
WritingTask:  book_id, unit, title, genre, requirements[](要求清单),
              rubric[](评分项), sample_essay_id, word_count_range, page_no

# 数学：例题与练习要能按类型定位，解题参照例题解法
MathProblem:  book_id, page_no, lesson, type: 例题|做一做|练习|复习|思考题,
              stem, solution_steps[], answer, kp_ids[],
              has_figure: bool, symbols_preserved: bool

# 数学：错因分类驱动复习路径
MistakeType:  概念性错误 | 计算失误 | 审题偏差 | 单位与格式错误 | 步骤缺失
```

### 5.3 KnowledgePoint / WikiEntry（L1/L2 知识层，见选型文档）

```python
KnowledgePoint: id, name, subject, first_grade, first_volume,
                appears_in: [(book_id, page_no)], prerequisites: [kp_id]
WikiEntry:      kp_id, definition, examples[], pitfalls[],
                citations: [(book_id, page_no)], generated_at, source_hash
```

### 5.4 学情

```python
LearnerEvent(L1):  ts, learner, surface(ask|solve|drill|grade|write),
                   subject, book_id, page_no, kp_id,
                   correct: bool|None, mistake_type: MistakeType|None, raw
LearnerProfile(L2): learner, grade, mastery: {kp_id: 0..1},
                    weak_points[], mistake_distribution{}, recent_mistakes[],
                    last_review_at   # Markdown，引用 L1 事件 id
```

文件化、可审计，不用隐藏向量库；家长可直接打开 `data/memory/<learner>/profile.md` 查看和修正。

## 6. 阶段二：parse 设计

### 6.1 流程（双通道）

```
构建期（一次性、离线）：
  ① 打开 PDF → 逐页抽取，判定通道
     平均字符数 < 50 → 整册标记 need_vlm（无文本层，16 册 1277 页）
  ② 通道 A｜文本层：PyMuPDF 逐页抽取 + 拼音字体映射修复
        → 字符级精确、严格保持原文顺序（权威）
  ③ 通道 B｜VLM：渲染页图 → 多模态模型转录
        → 版式语义、表格、图注、扫描页（理解型）
  ④ 合并：按页记录 source；有文本层的页以 A 为正文，B 只补充结构与图注
  ⑤ 抽取目录 → 单元/课边界 → 对齐到页
  ⑥ 学科结构化抽取（见 6.3）
  ⑦ 写 data/parsed/<book_id>.jsonl（页行 + 课行）+ 学科表
```

### 6.2 关键决策

| 决策 | 方案 | 理由 |
| --- | --- | --- |
| **双通道，而非单引擎** | 文本层为权威正文 + VLM 补充语义 | 实测：文本层+映射的拼音与 VLM **100% 一致**；但 VLM 会**重排顺序**（识字表页把第 8 课排到第 6 课之前、把「语文园地一」提前），不能作唯一权威来源 |
| **VLM 的定位** | 构建期一次性提取；无文本层册的唯一来源 | 全量 8384 页单线程需 35+ 小时；有文本层的 7107 页再走 VLM 是浪费（且引入顺序风险） |
| **拼音修复** | 字体映射（`HanyuXi-JZ`）而非 OCR / VLM | 实测本地 OCR 拼音不可用（`dirénniwóta` 粘连丢调）；映射零成本且与 VLM 逐条一致 |
| **扫描册** | 走 VLM 通道（1277 页，并发 8 约 50–60 分钟） | 实测能正确输出表格结构、注音与符号；本地 OCR 不行 |
| OCR 粒度 | 整册统一判定，不逐页混合 | 避免同册文本质量不一致导致切块错乱 |
| 目录获取 | 平台章节树 > PDF 目录页 > 正文规则 | 平台章节树最准；未接入时退回解析 |
| 公式处理 | V0 保留原文文本 + 记录所在页；不强行 LaTeX 化 | 公式识别错误率高，错误公式比不识别更糟 |
| **VLM 输出可回溯** | 保存 VLM 原始输出与模型版本 | 换模型/改提示词后可 diff，也能人工核对 |

### 6.3 学科差异化解析（★）

| 学科 | parse 阶段的额外要求 |
| --- | --- |
| **语文** | 抽取「识字表 / 写字表 / 词语表」（教材附录，格式规整，规则抽取即可）；课文按段落完整保留，**不做内容清洗**（文学性表达不能丢）；标注课文体裁与阅读策略单元 |
| **数学** | **符号与公式保真**（+、×、÷、=、分数排版、单位）；区分例题 / 做一做 / 练习 / 复习题；公式页 OCR 错误率高，数学册优先文本层，OCR 册须人工抽检公式页 |
| **英语** | 词汇表抽取；对话按角色分行 |
| **科学** | 实验步骤与**安全提示**要能定位（后续 Guard 用于安全校验） |

### 6.4 双通道提取（★）

| 维度 | 通道 A 文本层 | 通道 B VLM |
| --- | --- | --- |
| 实现 | PyMuPDF + 拼音字体映射 | 渲染页图 → 多模态模型转录 |
| 拼音 | **100%**（与 VLM 逐条一致） | 正确，但偶发漏行 |
| 汉字 / 符号 | 完美，`÷ × （ ）` 保真 | 正确 |
| **原文顺序** | **严格保持** | **会重排**（多栏、跨块时按视觉重组） |
| 版式语义 | 无（只有字符串） | **强**：表格、知识结构图、图注、标题层级 |
| 速度 | 毫秒/页 | 14–30 s/页 |
| 成本 | 0，离线 | API 调用 |
| 适用 | 78 册 7107 页（主力） | 16 册 1277 页 + 结构补充 |

**选择规则**：

```
if 该页有文本层:  source = "text_layer"（正文权威），VLM 结果只作 structure 附注
else:             source = "vlm"（唯一来源）
```

**顺序风险与校验**（实测证据）：VLM 转录识字表页时，把第 8 课排到了第 6 课之前、把「语文园地一」提到了汉字行前。因此：

- **凡是顺序敏感的内容**（识字表按课归类、课文段落、题号），一律以通道 A 为准；
- VLM 仅用于顺序不敏感的语义补充（表格内容、图注、结构层级）；
- 两者冲突时记录 `conflict`，供人工抽检。

**并发与耗时**：VLM 通道并发 8，1277 页约 50–60 分钟；文本层通道 4 并发，7107 页数分钟。

**插图理解纳入语料（★）**：教材里的图**不是装饰**——数学的几何图形、线段图、统计图，科学的实验装置与观察对象，少了图就读不懂题。所以扫描册走 VLM 时，提示词要求在图出现的位置插入：

```
[图N] 描述：图中画了什么、有哪些标注与数据、说明了什么规律或关系
```

图描述与文字转录在**同一次调用**内完成，不额外增加 API 成本。实测科学六下第 30 页输出 4 处描述（苔藓树干、松果球果、水稻、蕨类羽状复叶）；第 16 页把两张塔台设计图纸的标注（"上面：1个""侧面：2个"、三角形结构、底座塔身）还原成了文字。

> 注意：该模型是**推理型**模型，`max_tokens` 给小了会被推理 token 耗尽导致正文为空——默认已提到 8192，且 `content` 缺失时回退 `reasoning_content`。

文本层册的插图暂不单独处理（7107 页全量跑图理解不划算），后续按学科优先级补：**数学 > 科学 > 语文**（数学最依赖图）。

### 6.5 运行时多种方式（★）

构建期产出静态语料后，运行时 Agent 仍可按需要选择不同的内容获取方式——**VLM 适配器在构建期与运行期共用**：

| 方式 | 何时用 | 成本 |
| --- | --- | --- |
| 读 parsed 缓存（文本层） | 默认，绝大多数场景 | 0 |
| 读 parsed 缓存（VLM 结果） | 扫描册页面 | 0（构建期已付过） |
| **按需 VLM 解析指定页 / 图** | 教材里解释不清的插图、表格、实验装置图 | 每次一次 API |
| **按需 VLM 解析用户上传照片** | 孩子拍的作业题、试卷、手写作文 | 每次一次 API |
| 按需本地 OCR | 无网环境兜底 | 0 |

关键点：孩子拍一道作业题的照片 → 走**同一个 VLM 通道**转成文本 → 再进入 Agent 管线（判题、讲题、归因）。构建期与运行期复用一套 `VLMClient`，只是输入从"渲染的教材页"变成"用户上传的图片"。

> 因此 VLM 不是"构建期用完就扔"的工具，而是**贯穿构建期与运行期的基础能力**；构建期用它把教材变成语料，运行期用它把孩子的输入变成可处理的文本。

### 6.6 两阶段提取：构建期批量 + 运行期在线（★）

同一个 `VLMClient`，两个阶段共用，写的是**同一份产物**：

| 阶段 | 触发 | 输入 | 写哪里 |
| --- | --- | --- | --- |
| 构建期 | `parse` / `backfill` 命令 | 渲染的教材页 | `parsed/<book_id>.jsonl` + `vlm_raw/` |
| 运行期 | 孩子拍照提问、或问到没解析的页 | 上传图片 / 按需渲染的页 | 同上，**回填** |

```python
# 运行期在线提取（parse/online.py）
def transcribe_photo(image: bytes, prompt=None) -> str    # 孩子拍的题目照片 → 文本（含图描述）
def ensure_page(book_id: str, page_no: int, force=False) -> str   # 本地没有就当场解析并回填
def ensure_pages(book_id: str, page_nos: list[int]) -> dict       # 批量：并发解析，但只写一次盘
```

- 在线补出的页标记 `source=vlm_online`，与构建期的 `vlm` / `text_layer` 区分，meta 里累计 `online_pages`；
- 回填后进产物，下次直接命中（实测二次取同一页耗时 0.00s）。

**按需补的意义**：不是每册都值得预先批量跑。美术册整册约 1.5 小时而答疑价值很低；改成"问到哪一页补哪一页"，单次约 20 秒，补过就永久复用。**低价值册因此可以完全不进构建期计划。**

**断点续跑**：`vlm_raw/<book_id>/` 既是回溯证据，也是**缓存**。整册跑到一半中断，重跑时已解析的页直接复用，只补缺失页——实测中断在 63/94 页的册，重跑只补剩余部分，不浪费已完成页。

**单页失败不拖垮整册**：单页报错只把该页留空（`vlm_error` + 原因），已完成的页照常落盘；整册 meta 记 `failed_pages`，由 `backfill` 后续按页补。

### 6.7 全量核对与补齐

```bash

python -m agent_textbook backfill             # 核对 + 补齐（幂等，可反复跑）
```

三类缺口：

| 缺口 | 判定 | 补法 |
| --- | --- | --- |
| 空壳册 | 缺页 > 50%（扫描册） | 整册 VLM，断点续跑 |

## 7. 阶段三：index 设计

### 7.1 切块（分学科）

| 内容 | 策略 |
| --- | --- |
| 一般正文 | 按课切 → 课内按页 → 页内超长按 300–500 字滑窗（overlap 50–80 字）；**不跨课** |
| **语文课文** | **整篇不切块**，独立存 `LessonText`，检索时整篇注入（课文几百字，切块会破坏语境） |
| **语文字词** | 不进向量库，进 SQLite 字词表，走精确匹配 |
| **数学题** | 题目 + 解法步骤整体成块，标注 `type`，便于"找同类例题" |
| **习作** | 习作要求与 rubric 单独索引，供写作任务检索 |

### 7.2 索引

| 索引 | 用途 | 实现 |
| --- | --- | --- |
| 元数据表 | 硬过滤（学段/学科/版本/年级/册次/课） | SQLite `chunks` 表 |
| 向量索引 | 语义召回 | `sqlite-vec` 或 FAISS（3–5 万块，CPU 够用） |
| BM25 | 术语精确匹配（"分数的初步认识"） | `bm25s` |
| 页级索引 | 取某页原文 | SQLite `pages` 表 |
| **课文表** | 整篇课文存取 | SQLite `lesson_texts` |
| **字词表** | 精确查字 | SQLite `words`（按 `char`/`pinyin` 建索引） |
| **题库表** | 按类型/知识点找题 | SQLite `problems` |

### 7.3 检索流程

```
问题 + 作用域（年级/学科/册次/课）+ 学科 Profile 指定的检索策略
   ├─ ① 路由检索方式：查表 / 语义检索 / 整篇课文
   ├─ ② 元数据硬过滤：先框定「三年级·数学·上册」
   ├─ ③ 双路召回：向量 top-50 + BM25 top-50
   ├─ ④ RRF 融合 → top-20 → 重排 → top-5
   └─ ⑤ 连页码元数据一起交给 Agent
```

**过滤先于检索**：教材内容跨年级螺旋重复，不过滤必然串年级。

### 7.4 索引运维（借鉴 DeepTutor）

- **版本化**：重建写入 `data/index/v{N}/`，完成后切换指针；旧版保留，**重建中绝不破坏可用索引**。
- **单册增删**：换教材版本只重跑该册。

## 8. 阶段四：多 Agent 设计（核心）

### 8.1 为什么需要多 Agent

不是为了"多才显得智能"，而是四个具体问题：

1. **任务差异大**：讲解、解题、出题、批改、作文指导的提示词、输出格式、检索策略完全不同。塞进一个万能 prompt 会互相干扰。
2. **学科差异大**：语文作文和数学解题的"正确"定义不同（见 §9）。
3. **防幻觉需要独立裁判**：让生成答案的 Agent 自查编造，等于运动员兼裁判。
4. **对象适配**：同一知识点给一年级和六年级的讲法不同；给孩子的讲法和给家长的辅导话术也不同。

### 8.2 角色清单

| Agent | 职责 | 是否需 LLM | 说明 |
| --- | --- | --- | --- |
| **Router 调度** | 判断 `subject + capability + scope`（语文·字词 / 数学·解题 / 语文·习作 …） | 小模型或规则 | 作用域缺失则 `ask_user` 追问 |
| **Planner 检索规划** | 拆检索计划：查表 / 语义 / 整篇课文；查询改写；是否跨册 | 是（小模型） | 一题多问时拆成多个子查询 |
| **Retriever 检索** | 执行检索，返回带页码片段 | 否 | 确定性，可缓存 |
| **Teacher 主讲** | 按 `年级 × 学科` 话术讲解；解题时输出分步链 | 是（主模型） | 事实句带 `[册次·页码]` |
| **Quizzer 出题** | 按课/知识点出题，附答案与出处 | 是 | 两阶段：先定题型分布，再逐题生成 |
| **Grader 批改** | 判分 + 错因归因（数学按 `MistakeType`）+ 建议 | 部分 | **判对错用规则**（字词/计算），**解释错因用 LLM** |
| **Guard 校验** ★ | 按模式校验，见 §9.2 | 是（小模型）或规则 | **硬约束执行者**，独立于 Teacher |
| **Coach 陪练** | 鼓励式、分步提示、不直接给答案 | 是 | 用于做题过程中的引导 |
| **Parent 家长视角** | 转成家长可用的辅导话术 + 易错点提示 | 是 | 同一内容的不同受众 |
| **Learner 学情** | 记录错题、更新掌握度与错因分布 | 否（规则） | 写 L1 事件 + L2 画像 |

### 8.3 Agent Runtime（借鉴 DeepTutor）

所有能力共享**一个循环**，不同能力是不同的 pipeline 编排：

```python
def run(turn: Turn) -> Answer:
    profile = subjects[turn.subject]              # 学科 Profile 决定工具与 Guard 模式
    tools   = mount_tools(profile, turn.capability)
    for round in range(MAX_ROUNDS):               # 建议 6
        msg = llm.chat(messages, tools=tools)     # think
        if not msg.tool_calls:
            return finalize(msg)                  # 不带工具调用的消息 = 结束
        for call in msg.tool_calls:
            if call.name == "ask_user":           # 暂停回合，追问后恢复
                return pause_and_ask(call.args)
            messages.append(tool_result(call))    # observe
    return Answer(refused=True)                   # 超轮次：保守拒答
```

要点：

- **工具按学科 + 能力挂载**：数学挂 `gen_mental_math`、`check_answer`；语文挂 `lookup_word`、`read_lesson`。不一次性塞满。
- **上下文两类**：*sticky*（年级、学科、版本、册次、persona、学情、当前课）跨回合持久；*one-time*（某页、某题、某篇课文）单次注入。
- **超轮次即拒答**（事实类）；创作类不适用拒答，见 §9.2。

### 8.4 工具集

| 工具 | 作用 | 主要学科 |
| --- | --- | --- |
| `search_textbook(query, scope, top_k)` | 混合检索，返回带页码片段 | 全部 |

### 8.5 协作模式

**① 管线式（答疑 / 讲解 / 解题）**

```
Router → Planner → Retriever → Teacher → Guard(按模式) → 输出
                                  ↑         │
                                  └─────────┘ 不通过则重写（≤2 轮）
```

**② 角色切换式（同一 loop 换 persona）**

```
讲解 → Teacher（讲清楚）
陪练 → Coach（分步提示，不直接给答案）
家长 → Parent（辅导话术 + 易错点）
```

**③ 对抗校验式（Guard）**：见 §9.2 三模式。

### 8.6 成本与延迟控制

| 手段 | 做法 |
| --- | --- |
| 小模型下沉 | Router / Planner / Guard 用轻量模型，主模型只给 Teacher |
| 能规则就不用 LLM | 字词判对错、计算判分、口算生成、查表全部确定性实现 |
| Retriever 不调 LLM | 仅 Planner 做查询改写时用一次 |
| Guard 分级 | 先规则校验，抽样或小模型复核 |
| 缓存 | 同 `scope + question` 命中直接返回 |
| 轮次上限 | ≤ 6 轮，超了保守拒答 |

**目标**：一次普通问答 ≤ 3 次 LLM 调用；**字词查询与口算练习 0 次 LLM 调用**。

## 9. 学科差异化设计（★ 核心）

### 9.1 根本差异：三类任务的「正确性」定义不同

| 任务 | 正确性的定义 | 能否要求"每句有原文依据" |
| --- | --- | --- |
| 语文字词（"爽"的笔顺、组词） | 答案唯一，可查表 | 能（查表即依据） |
| 语文阅读理解 | 答案在课文中 | 能（须定位到段落） |
| 语文习作（作文） | **没有唯一答案**，只有"是否符合习作要求" | **不能**——创作不是引文 |
| 数学解题 | 结论可验算，过程是**推导**出来的 | **不能**——推导步骤无原文出处 |
| 数学概念讲解 | 定义来自教材 | 能 |
| 口算练习 | 程序化生成 + 确定性判分 | 不涉及 |

**这是本项目最容易踩的坑**：若用同一套「每句必须有出处」的 Guard 管所有学科，结果必然是——作文被卡死（每句都要出处）、数学解题被卡死（推导步骤没有出处）、而字词题反而过度设计（本来查表就行，却走了一遍语义检索 + LLM 生成）。

### 9.2 Guard 三模式（关键设计）

| 模式 | 适用 | 校验什么 | 不通过的处理 |
| --- | --- | --- | --- |
| **strict** 事实溯源 | 概念答疑、字词、阅读理解、道法情境题 | 每句能否在检索片段 / 课文中找到依据 | 删除无依据句；核心结论无依据 → **整条拒答**「教材里没有」 |
| **derivation** 推导有效 | 数学解题、算理说明 | ① 前提与结论有教材依据；② 中间步骤**逻辑有效、无跳步**；③ 可验算的结论必须验算通过 | 标出跳步 → 要求补步；验算不过 → 重算 |
| **rubric** 量规评价 | 习作、开放性表达、口语交际 | 是否符合习作要求清单、年级语言水平、字数/格式/体裁 | 按量规给分项反馈与修改建议；**不溯源、不拒答** |

配套规则：

- **拒答只用于 strict**。孩子问"怎么写这篇作文"，回答"教材里没有"是荒谬的。
- **derivation 的引用是分层的**：`[依据: 三上·数学·P68 例题]` 标注前提与所用规则，`[推导]` 标注推理步骤——让读者一眼分清"哪句是书上说的，哪句是推出来的"。
- **rubric 的量规来自教材**：习作单元的要求清单就是 rubric，不是模型自己编的标准。

### 9.3 语文设计

三块能力的数据形态、检索、校验完全不同，必须分开设计：

| 能力 | 数据形态 | 检索方式 | 校验 | 特殊设计 |
| --- | --- | --- | --- | --- |
| **字词基础** | 结构化表：识字表 / 写字表 / 词语表 / 多音字 / 近反义词 | **精确查表**（SQLite），**不走语义检索、不调 LLM** | 确定性判对错 | 笔顺、部首、笔画数需字典数据；听写需 TTS（V1） |
| **阅读理解** | 整篇课文 + 课后题 | **整篇注入**（课文几百字，**不切块**） | strict：答案须在课文中定位并给出段落 | 按**阅读策略单元**组织提问：四年级"提问"（针对内容/写法/联系生活）、五年级"提高阅读速度"、六年级"有目的地阅读" |
| **习作（作文）** | 习作要求 + 习作例文 + rubric | 检索本册习作单元要求与例文结构 | **rubric**：对照要求清单逐条评分 | 给**写作支架**（提纲/句式/素材），**不代写整篇** |

语文特有设计点：

- **课文整篇存取是硬要求**。切块会破坏叙事与语境，阅读理解必然答不准。所以 `lesson_texts` 表独立于 chunks。
- **字词表要规则抽取**（教材附录格式规整），准确率要求接近 100%；这是"抽取"不是"生成"，不能让 LLM 编。
- **不代写作文**：直接给整篇范文对孩子有害且无效。设计为「支架 + 片段示范 + 按 rubric 自评 + 修改建议」。
- **背诵与朗读**：需要原文精确输出（V0 文本，V1 加 TTS）。
- **古诗文**：需注释、译文、作者背景——教材内有注，超出部分要标注来源，否则按 strict 应拒答。

### 9.4 数学设计

| 能力 | 特点 | 检索 | 校验 |
| --- | --- | --- | --- |
| **概念讲解** | 教材定义 + 例题 | 语义检索 | strict |
| **算理（为什么这样算）** | 如"为什么数位要对齐"、"为什么除以分数等于乘倒数" | 检索定义 + 例题 | strict + 分步 |
| **解题** | 分步推理链 | 检索**同类例题**作解法参照 | **derivation** |
| **口算/计算练习** | 程序化生成，**不需要检索** | 无 | 确定性判题，**不调 LLM** |
| **错题归因** | 错因分类 | 检索对应知识点 | 归因到 `kp_id` + `MistakeType` |

数学特有设计点：

- **解题必须分步输出**，每步标注依据类型：

  ```
  ① 25×4 = 100          [推导]
  ② 100÷5 = 20          [推导]
  ③ 验算：20×5÷4 = 25 ✓  [验算]
  依据：四则运算顺序 [依据: 三上·数学·P68 例题]
  ```

- **错因分类驱动复习路径**（数学 Agent 最有价值的输出）：

  | 错因 | 复习动作 |
  | --- | --- |
  | 概念性错误 | 回看对应例题与定义（strict 讲解） |
  | 计算失误 | 推送同型口算练习（`gen_mental_math`） |
  | 审题偏差 | 推送同类题做审题训练（圈关键词） |
  | 单位与格式错误 | 针对性格式提醒 + 少量练习 |
  | 步骤缺失 | 要求写出完整步骤并逐步批改 |

- **判分用规则，解释用 LLM**：答案对不对是确定的（字符串/数值比对），不该让 LLM 掷骰子；LLM 只负责解释错因与给建议。
- **一题多解**：同一题生成 2–3 种解法再对比（多轮 Teacher 生成 + 对比），培养思维灵活性——这是数学"思维训练"的核心，而非刷题。
- **符号保真**：解析阶段必须保住数学符号；数学册优先文本层，OCR 册须人工抽检公式页（错误符号会直接教错孩子）。

### 9.5 其它学科

| 学科 | 特点 | 设计要点 |
| --- | --- | --- |
| **英语** | 词汇表 + 对话 + 语法 | 词汇走查表；对话走模板 + 角色扮演；需 TTS 跟读（V1） |
| **科学** | 探究流程（提问→猜想→实验→结论） | **安全提示是硬要求**：涉及实验必须输出成人陪同提醒；探究过程按流程引导而非直接给结论 |
| **道德与法治** | 情境价值判断 | 答案须回到教材观点（strict）；不做开放讨论，避免价值相对化 |

### 9.6 架构落地：学科 Profile 参数化

**不为每个学科写一套 Agent**，而是同一套 Agent + 学科 Profile：

```python
@dataclass
class SubjectProfile:
    subject: str
    capabilities: dict[str, Capability]   # 字词 / 阅读 / 习作 / 解题 / 口算 ...
    # 每个能力声明：检索方式、Guard 模式、挂载工具、输出模板
    retrieval_default: Literal["lookup", "semantic", "whole_text"]
    guard_mode: dict[str, Literal["strict", "derivation", "rubric"]]
    tools: list[str]
    output_templates: dict[str, str]      # 讲解 / 解题 / 习作的输出骨架
    eval_sets: dict[str, str]             # 学科 × 能力的评测集
    parse_hooks: list[str]                # 该学科在 parse 阶段的额外抽取
```

Router 输出 `(subject, capability, scope)` → 加载 Profile → 选 pipeline + Guard 模式 + 工具集 + 输出模板。

新增学科 = 新增一个 Profile 文件，不动 Agent 主体。

### 9.7 学科差异化对前序阶段的反向影响

这不是只在 Agent 层的事，会一路反向影响 parse / index / eval：

| 阶段 | 语文 | 数学 |
| --- | --- | --- |
| **parse** | 抽取识字表/写字表/词语表；课文按段完整保留、不做清洗 | 符号与公式保真；区分例题/做一做/练习/复习题 |
| **index** | 课文整篇另存**不切块**；字词进 SQLite 表走精确匹配 | 题目+解法整体成块，按 `type` 与 `kp_id` 索引 |
| **eval** | 字词确定性评测、阅读理解定位准确率、习作 rubric 评分一致性 | 解题步骤完整性、验算正确率、错因归因准确率 |
| **工具** | `lookup_word` / `read_lesson` / `get_rubric` | `lookup_problem` / `gen_mental_math` / `check_answer` |

## 11. 质量保障

### 11.1 检索评测（借鉴 DeepTutor `kb eval`）

`data/eval/retrieval.jsonl`，每行 `{"query", "scope", "gold": [片段], "answerable"}`，指标：**Recall@k / Precision@k / nDCG@k / MRR / MAP / Hit@k**。

**指标是排序的纯函数，不用模型当裁判** —— 结果可复现、可 diff。保存 baseline 后，任何切块/嵌入/重排改动都跑一遍，回落即告警。

### 11.2 分学科端到端评测

| 学科·能力 | 指标 | 目标 | 判定方式 |
| --- | --- | --- | --- |
| 语文·字词 | 查表准确率 | ≥ 99% | **确定性**（对表里答案） |
| 语文·阅读理解 | 答案定位准确率 | ≥ 85% | 人工标注段落 |
| 语文·习作 | rubric 评分与教师评分相关性 | ≥ 0.7 | 人工抽评 |
| 数学·概念讲解 | 引用准确率 | ≥ 90% | strict 自动 + 抽检 |
| 数学·解题 | 最终答案正确率 / 步骤完整率 | ≥ 90% / ≥ 85% | **答案确定性验算**，步骤人工抽检 |
| 数学·错因 | 归因准确率 | ≥ 80% | 人工标注 |
| 数学·口算 | 生成合法性与判分正确率 | 100% | 确定性 |
| 通用·拒答 | 不可答问题的拒答正确率 | ≥ 95% | **最重要** |
| 通用·Guard | 漏检率 / 误杀率 | 漏检 ≤ 3% / 误杀 ≤ 10% | 人工标注集 |

### 11.3 多 Agent 专项评测

| 对象 | 测什么 |
| --- | --- |
| Router | 意图分类准确率、**学科+能力**抽取准确率 |
| Planner | 查询改写后召回是否提升；检索方式选择是否正确（查表 vs 语义） |
| Teacher | 年级适配度（人工 1–5 分）、引用完整率 |
| Guard | 三模式各自的漏检率与误杀率 |
| Quizzer | 题目与课匹配度、答案正确性、出处正确率 |
| Grader | 判分准确率（应等于确定性判定）、错因归因准确率 |

Guard 的**漏检率**是最需要盯的指标——它一旦放水，整个系统的可信度就塌了。

### 11.4 回归

```powershell
python -m agent_textbook eval --set data/eval/retrieval.jsonl --baseline baseline.json
python -m agent_textbook eval --subject 语文 --capability 字词
python -m agent_textbook eval --subject 数学 --capability 解题
```

## 14. 实施计划

| 里程碑 | 内容 | 交付物 |
| --- | --- | --- |
| **M0a 文本层通道** | `parse/extract`：**PyMuPDF + 拼音字体映射** + 目录解析 + **学科表抽取**（语文字词表、数学题型标注） | 78 册解析完成，拼音 100% |
| **M0b VLM 通道** | `VLMClient`（**构建期与运行期共用**）+ 扫描册提取 + 与文本层**交叉校验**与冲突标记 | 16 册解析完成，冲突可查 |
| **M1 检索** | `index`：切块 + 向量 + BM25 + **课文整篇表 / 字词表 / 题库表** + 元数据过滤 | `search` 可用 |
| **M2 单 Agent** | `agents/runtime`：一个 loop + 工具；Teacher 单角色 + strict 引用约束 | `ask` 可用（先只做事实类） |
| **M3 数学线** | `subjects/math.py`：**解题分步 + derivation Guard + 验算 + 错因分类 + 口算生成** | `solve` / `drill` 可用 |
| **M4 语文线** | `subjects/chinese.py`：**字词查表 + 阅读理解整篇 + 习作 rubric 指导**（不代写） | 字词/阅读/写作指导可用 |
| **M5 多 Agent 完整** | Router / Planner / Quizzer / Grader / Coach / Parent / Learner 上线 | 全能力 |
| **M6 评测** | 检索评测 + 分学科端到端 + Guard 漏检/误杀 + 回归门 | 指标达标 |
| **M7 增强** | 记忆三层、掌握度、家长视角、TTS 听写、扫描册 OCR 完善 | 完整能力 |

**顺序理由**：M0–M2 先打通「事实类」单 Agent 闭环（这是 strict 模式，最严格、也最容易验证）；M3/M4 再分别攻克数学（推导类）与语文（查表 + 创作类）——这两条线的校验机制本质不同，分开做才能各自调优，混在一起会导致 Guard 规则互相妥协。

**先数学后语文**：数学的 derivation 有客观验算标准（答案对不对可自动判），容易测；语文的 rubric 需要人工校准，成本更高。先拿下可自动验证的部分。

## 15. 风险登记

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 扫描版无文本层（科学/美术/书法 16 册 1277 页） | 这些册检索不到 | **VLM 通道**提取；标记 `source=vlm`，评测单列 |
| **VLM 重排原文顺序** | 识字表按课归类、课文段落错乱 | 顺序敏感内容一律以文本层为准；VLM 只作语义补充；冲突写 `conflict` 待抽检 |
| VLM 输出不稳定（换模型 / 改提示词） | 语料不可复现 | 保存 `data/vlm_raw/` 与模型版本，可 diff 回溯 |
| 物理页码 ≠ 书上页码 | 引用页码错 | 建映射表；V0 注明"PDF 第 N 页" |
| **数学符号 OCR 出错** | **教错孩子** | 数学册优先文本层；OCR 册人工抽检公式页；`symbols_preserved` 标记 |
| **语文课文切块破坏语境** | 阅读理解答不准 | 课文整篇另存不切块（§7.1） |
| **字词让 LLM 生成** | 编造拼音/笔顺 | 强制规则抽取 + 查表返回，字词路径禁用 LLM 生成 |
| **作文被 strict Guard 卡死** | 功能不可用 | Guard 三模式，创作类走 rubric（§9.2） |
| **代写作文/作业** | 对孩子有害 | 只给支架与片段示范，产品层面禁止输出完整成品 |
| LLM 用自身知识编造 | 误导孩子 | Teacher 引用约束 + Guard 独立校验 + 拒答路径 |
| 多 Agent 放大延迟与成本 | 体验差 | 小模型下沉、规则替代 LLM、缓存、轮次上限 |
| 多 Agent 角色间不一致 | 同一问题两次答案不同 | 共享 sticky 上下文与同一批检索片段；Teacher 是唯一事实讲述者 |
| Guard 过严导致误杀 | 正常讲解被拒 | 调阈值；漏检率/误杀率双指标监控 |
| 换教材版本 | 答案过时 | 产物按版本隔离；索引版本化 + 单册重跑 |
| 依赖体积大（torch） | 安装困难 | 可选 ONNX 方案 |
