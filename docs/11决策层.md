## 5. 决策层：多 Agent 编排（★ 补充）

> 存储层解决"**知识在哪**"，决策层解决"**谁来用、怎么用、怎样保证说得对**"。
> 本节只做**选型论证**（要不要多 Agent、角色怎么切、边界在哪）；
> 模块划分与代码结构见 `05Agent运行时.md` §8.3。

### 5.1 为什么不是"一个模型 + 检索"

| 失败模式 | 原因 |
| --- | --- |
| 顾此失彼 | 一次回答要同时检索、解题、出题、批改，单 prompt 下相互干扰 |
| **自评失效** | **让生成者校验自己的答案 = 没有校验**（模型会为自己的错误找理由） |
| 学科差异无处安放 | 语文要溯源、数学要分步、英语要词表校验，塞进一个 prompt 会互相污染 |

→ 结论：**校验必须与生成分离**。Guard 是独立角色，看不到 Teacher 的"意图"，只看产物与证据。

### 5.2 角色最小集

`Router → Planner → Retriever → Teacher → Guard → Presenter`

| 角色 | 职责 | 可省 |
| --- | --- | --- |
| Router | 判定学科 / 能力 / 作用域（年级·册·课） | 否 |
| Planner | 拆解步骤、选工具 | **可**（简单问题短路） |
| Retriever | 按学科策略取（查表 / 语义 / 整篇） | 否 |
| Teacher | 按学科流程生成（如数学"解题四步"） | 否 |
| **Guard** | **独立于生成**：三模式校验 + 超纲拦截 | **否** |
| Presenter | 决定呈现形态 | 是（默认文本） |

**不为炫技而多**：能查表直返的问题（"第 3 课生字"）**不起 Planner / Teacher**，路由后短路。
多 Agent 是**按需装配**，不是每次全套。

### 5.3 ★ 决策层对存储层的硬约束（本文真正关心的）

| 决策层需要 | 存储层必须提供 |
| --- | --- |
| Guard 校验"有没有依据" | 检索结果**必须带 `book_id` / `page_no` 引用** |
| Router 决定去哪查 | 知识**分层且可判别**（精确表 / 文本块 / 要素表） |
| Guard 校验"超不超纲" | 知识点挂**册次与课**（`kp_id → book / lesson`） |
| 英语词汇范围校验 | 词汇表能**按册精确查**（不是语义近似） |
| 数学验算 | 题目有**结构化 `answer`**（不是段落文本） |
| 科学安全拦截 | 实验条目带**安全标记** |

→ **"返回引用"不是锦上添花，而是 Guard 存在的前提。**
存储层若只返回"相似文本片段"，溯源、超纲拦截、拒答**全都无从谈起**——
这也是 §4.2「RAG 必须是底座」的另一半理由：**底座要能给出坐标，不只是相似文本。**

### 5.4 确定性优先

能查表的不检索，能规则的不调模型：字词、词汇、页码、目录、判对错**全部确定性**；
模型只用于**必须生成的环节**（讲解、出题、批改、习作）。

### 5.5 ★ 学校角色模型：人格层与工程层的映射

**能不能把多 Agent 映射成学校里的真实角色？能，而且值得**——理由是职责边界清晰
（学校分工是现实验证过的），且家长与孩子能理解"数学老师"，理解不了"Teacher Agent"。

**但风险同样明确**：为"像学校"造出一堆没有职责的角色（校长、年级主任…）——那是表演，不是工程。
判断标准只有一条：**去掉这个角色，系统是否缺一块功能？**

#### 5.5.1 实证：教材自己就在设计"同伴 / 协作"学习

| 教材词 | 页数 | 主要分布 |
| --- | --- | --- |
| **说一说** | **618** | 数学 225、美术 130、科学 74 |
| 交流 | 438 | 语文 226、道法 65、科学 62 |
| 合作 | 205 | 音乐 88、科学 27 |
| 小组 | 192 | 数学 50、科学 46、道法 41 |
| 讨论 | 167 | 数学 52、科学 51 |
| 同桌 | 38 | 数学 19、道法 11 |

→ **"说一说"以 618 页居首**：教材大量要求孩子**说出来、讲给别人听**。
但在 40 人的班级里，"两两说""小组讨论"恰恰是**被跳过最多的环节**。
**AI 在这里补的不是知识，而是班级授课制必然丢掉的交流机会。**

#### 5.5.2 角色表（★ 缺口不在"学科老师"）

| 学校角色 | 工程对应 | 职责 | 现状 |
| --- | --- | --- | --- |
| **班主任** | Router + 调度 | 分诊、**跨学科学情统筹**、决定谁出场 | ❌ **最大缺口** |
| 各科老师 | Teacher + SubjectProfile | 本科教学 | ✅ 已有（系统设计 §9.8） |
| **教研组长** | Guard | 把关：超纲、难度、正确性 | ✅ 已有，隐喻可直接复用 |
| **教务** | 进度模块 | 学到哪、今天练什么、复习排期 | ⭕ 有数据、无角色 |
| **心理老师** | 情感与动机 | 受挫干预、鼓励、给台阶的时机 | ❌ 画像有字段、**无角色承担** |
| **同桌** | 同伴学习 | 一起说、互相考、**让孩子讲给 AI 听** | ❌ 教材 618 页支持 |

→ **一个反直觉的结论**：直觉上最容易想到"每个学科配一个老师"，
但**学科老师恰恰是最不需要新建的**——`SubjectProfile` 已经承担了这件事（§5.2、系统设计 §9.8）。
真正缺的是**班主任（全局调度）、教务（排期）、心理老师（动机）、同桌（说出来）**——
这四个角色在系统里目前**没有承担者**，它们的功能散落在画像字段与进度模块里，无人负责。

**班主任尤其关键**：学科老师只看得见自己那一科，**只有班主任看得见完整的孩子**
（数学弱但语文强 → 时间怎么分配？今天先练哪科？）。这是当前架构缺失的一层。

#### 5.5.3 两层是映射，不是两套系统

```
人格层（对外可理解）  班主任 / 数学老师 / 教研组长 / 教务 / 心理老师 / 同桌
                              ↕  一一映射
工程层（对内可实现）  Router / Teacher+Profile / Guard / 进度模块 / 动机策略 / 同伴模式
```

**只维护工程层**，人格层是它的**表述**（提示词、称谓、话术），不写两套逻辑。
否则 N 个学科 × M 个流程步骤 = N×M 份维护，必然失控——
这正是 §9.8「不为每个学科写一套 Agent」要避免的。

#### 5.5.4 硬约束

1. **★ 一次只有一个角色对孩子说话**——发言权由班主任（Router）决定。
   多角色同时输出，孩子不知道听谁的；**这是多 Agent 面向儿童时最大的体验风险**。
2. **角色必须承担真实职责**，否则不建（不设"校长""教导主任"这类虚职）。
3. **角色数上限 ≤ 7**，超出即说明职责切分出了问题。
4. **★ 同桌角色必须诚实**：AI 扮"不懂的同学"让孩子教，要先说明是游戏
   （"我们来玩个小老师游戏，你讲给我听"），**不能假装真不懂**让孩子事后发现被骗。

**同桌的教育价值**：Learning by teaching 是最有效的学习方式之一，
而教材 618 页"说一说"本就要求孩子说出来——AI 正好提供了班级里没有的听众。

### 5.6 Agent 框架技术选型

#### 5.6.1 现状约束（实证）

| 事实 | 值 |
| --- | --- |
| 现有依赖 | **仅 `requests`**（`pyproject.toml`：`dependencies = ["requests"]`） |
| 现有 LLM 调用 | OpenAI 兼容 `/v1` 接口，**`requests` 直调**（VLM 转录已在用） |
| 运行环境 | 需支持本地离线（隐私：孩子数据不出本机，§8.12.5） |

→ 两条硬约束：**依赖要少**、**模型要可换**。
好消息是现有调用方式本就走 OpenAI 兼容协议，**换 `base_url` 即可切本地 Ollama / vLLM**。

#### 5.6.2 候选评估

| 候选 | 设计假设 | 适配 | 结论 |
| --- | --- | --- | --- |
| **自研薄编排层** | 无（自己定） | ★★★ | **选它** |
| LangGraph | 显式状态图 + checkpoint | ★★ | 唯一合理的现成候选 |
| AutoGen / CrewAI | **多 LLM Agent 自由协作** | ✗ | **错配，见 5.6.3** |
| OpenAI Agents SDK | 轻量 handoff | ★ | 自研即可覆盖，不必引依赖 |
| Dify / 低代码 | 云端可视化编排 | ✗ | 无法本地嵌入、黑盒、不可审计 |

#### 5.6.3 ★ 为什么主流"多 Agent 框架"是错配

主流框架卖的是"**多个 LLM Agent 互相讨论、协商、涌现解法**"（AutoGen 群聊、CrewAI 分工）。
而我们要的是**单 Agent + 工具循环 + 硬护栏**——**不需要 Agent 之间协商**，
只需要一个 Agent 自主地选工具、决定走几步。

→ 框架的**核心能力（Agent 间对话、角色协商、涌现解法）用不上**，
而它的**代价（不可控、延迟、成本、黑盒）全要承担**。

**★ 必须区分两件事**（不要因为"要 Agent"就引入多 Agent 框架）：

| | 结论 |
| --- | --- |
| **Agent 循环**——模型决定下一步做什么 | ✅ **要**（入口灵活，见 5.6.4） |
| **多 Agent 协商**——多个模型互相讨论 | ✗ **不要**（不可控、昂贵、无必要） |

我们要前者，主流框架卖的是后者——**这是两件事**。
§5.5 的"学校角色"是**人格与职责划分**，不是多个模型并行跑：
同一时刻只有一个 Agent 在动，角色只是它此刻的身份与工具权限。

#### 5.6.4 结论：以 Agent 为主（不是固定 workflow）

**★ 修正**：把执行写成固定管线（①→⑥）是错的——**入口高度灵活**，
不同入口触发的能力组合完全不同，步骤数、工具、是否追问都不同。
执行方式应是 **Agent**：由模型决定"做什么、用什么工具、要不要追问、做完了没有"。
这与 `05Agent运行时.md` §8.3 的 `run()`（模型驱动循环 + 轮次上限）一致。

**（1）入口不是一种，是六种**

| 入口 | Agent 行为 | 主要工具 |
| --- | --- | --- |
| 提问 | 检索 → 讲解 / 解题 | `search_textbook` / `read_lesson` |
| **上传作业 / 卷子** | VLM 提取 → 逐题批改 → 归因 → 复习建议 | `parse_sheet` / `diagnose` / `make_plan` |
| **预习** | 定位下一课 → 讲解 → 小测 | `list_lessons` / `read_lesson` |
| **复习** | 取薄弱点 → 出针对性练习 → 复测 | `read_memory` / `lookup_problem` |
| 习作 | 给支架 → 起草 → rubric 评分 | `get_rubric` |
| 追问 / 改口 | 多轮上下文，可中断、可改需求 | — |

→ **它们不是六条固定管线**，而是**同一套 Agent + 不同的工具子集与能力提示**。
尤其**预习与复习不是单轮问答，而是一段有节奏的多轮过程**（讲 → 练 → 评 → 结），
需要 Agent 维持计划与会话状态——这恰恰超出固定 workflow 的表达能力。

**（2）★ 护栏放在出口，不放在路径上**

既然要 Agent 的灵活性，就不能靠"限制它只能走哪几步"来保证安全——那等于把 Agent 退回 workflow。
正确做法是**卡住出口**：

| 约束 | 实现 |
| --- | --- |
| **任何面向孩子的输出必须经 `submit_answer`** | 该工具内部**强制触发 Guard**，不通过则返回错误让模型重写（≤N 次） |
| 确定性环节用工具承载 | `lookup_word` / `check_answer` / `gen_mental_math` 内部 **0 次 LLM** |
| 学科流程（如数学"四步"） | prompt 模板 + Guard 校验，**不是硬编码步骤** |
| 安全网 | 轮次上限 + 超时 + 超轮次保守拒答 |

→ **模型可以自由决定路径，但走不到"不经 Guard 就输出"这条路上。**
这比"限制循环"更好：既保住灵活性，又让 Guard 不可绕过。

**（3）★ 混合粒度：workflow 封装成工具，由 Agent 调度**

"以 Agent 为主"**不排斥 workflow**——某些环节用固定管线更好。判据只有一条：

> **"这几个步骤是否每次都一样、且能独立测试？"
> 是 → 封装成工具（内部是固定管线）；否 → 留给 Agent 自由走。**

| 环节 | 形态 | 理由 |
| --- | --- | --- |
| **Guard 校验** | **workflow** | 每次必过，**不能让模型决定"这次要不要校验"** |
| **上传卷子处理** | **workflow**（固定 4 步） | 提取 → 判分 → 归因 → 出计划，顺序固定、各步可单独测 |
| **批改** | 混合 | 判分（确定性）→ 归因（LLM）→ 建议（LLM），**顺序固定** |
| **练习 / 测验循环** | workflow | 出题 → 判分 → 记录 → 下一题，固定节奏 |
| **口算 / 听写生成** | workflow（0 次 LLM） | 纯程序，模型参与无价值 |
| **多形态渲染** | workflow | `ContentPlan` → 模板渲染 |
| **离线批处理** | workflow | 教材解析 / VLM 转录 / 建索引 |
| 讲解、探究引导、习作指导 | **Agent** | 要按孩子的反应调整，**步骤不固定** |
| 追问与澄清 | **Agent** | 强依赖上下文 |
| 跨入口任务规划 | **Agent** | 入口不同，路径不同 |

→ **workflow 以"工具"的形态存在**：`grade_sheet()` 内部是固定四步，
Agent 决定**何时调用它**，但**内部步骤不由模型改动**。

```
Agent（自由决定路径）
 ├─ grade_sheet()     → 内部是固定 4 步 workflow
 ├─ check_answer()    → 确定性，0 次 LLM
 └─ submit_answer()   → 内部强制 Guard（不可绕过）
```

这样"混合"是**工程上清晰的**：不是"有时用 workflow、有时用 Agent"这种模糊说法，
而是 **workflow 就是工具的一种实现**——Agent 负责调度，工具负责确定性。

（在线交互用 Agent、离线批处理用 workflow 的整体划分依然成立：
本项目前半段 collect → parse → index 本来就是 workflow，后半段面对孩子才是 Agent。）

**（4）工程要点**

- **工具调用用原生 function calling**（OpenAI 兼容协议，`requests` 直调，与现有 VLM 调用一致）。
- **模型适配层 `llm.py`**：环境变量切 `base_url` / `model` → 云端 API 或本地 Ollama / vLLM。
- **持久化不依赖框架**：用 §8.12.7 的 JSONL 事件流——明文、可重放、可审计，
  比框架的黑盒 checkpoint 更契合"家长能看"的要求。
- **依赖策略**：核心保持精简（现状仅 `requests`），新增依赖进 `optional-dependencies`。

#### 5.6.5 模型分层（成本与延迟）

| 环节 | 选型 | 理由 |
| --- | --- | --- |
| 字词 / 词汇 / 验算 / 判对错 | **规则，0 次 LLM** | 确定性 |
| Router 分类、Guard 校验 | 小模型或规则 | 高频、要求低延迟 |
| 讲解 / 出题 / 批改 / 习作 | 主模型 | 质量敏感 |

**延迟**：孩子等不了 30 秒 → 流式输出 + 检索并行 + Guard 走小模型。

**离线与在线分离**（与现状一致）：

| 场景 | 模型 |
| --- | --- |
| **离线批处理**（教材解析、VLM 转录） | 可调云端 API（一次性、**不涉孩子数据**） |
| **在线交互**（回答孩子） | 默认本地模型，云端可选 |
